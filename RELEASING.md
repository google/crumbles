# Releasing Crumbles

This document describes how to cut an official Crumbles release so that:

1. Gradle dependency and plugin artifacts are verified against committed
   SHA-256 metadata before building.
2. Users, helpline operators, and partner organizations have a published
   **signing certificate SHA-256 fingerprint** in every GitHub release note to
   compare against a downloaded APK, and against the installed APK copied off
   the phone as described in
   **[HOW_TO.md](HOW_TO.md#verifying-a-provisioning-qr-code-before-you-scan-it)**.

> **Note:** The `./gradlew` steps below need JDK 17 or newer and the Android
> SDK with the Android 15 (API level 35) platform, which Gradle finds through
> the `ANDROID_HOME` environment variable or `sdk.dir` in `local.properties`
> (see [Building from Source](HOW_TO.md#building-from-source-developers)).

---

## 1. Prepare the Release Commit

Before tagging a release, update these files in the commit that the tag will
point to:

1. `build.gradle.kts`: increase `versionCode` by one and set `versionName` to
   the number of the release. Android only replaces an installed app with an
   APK that has a higher `versionCode`.
2. The release tag in `APK_URL` in `setup_device.sh`, `setup_device.command`
   and `setup_device.bat`, and in the default download URL of
   `tools/generate_qr_payload.sh`.
3. `documentation_images/provisioning_qr.png`, if the release signing key
   changed. Generate the payload as section 4 describes, with the download URL
   `https://github.com/google/crumbles/releases/latest/download/CrumblesApp.apk`,
   and encode it as a QR code. Decode the image again and compare the result
   with the payload before you commit it. Because the code always downloads the
   latest release and pins only the signing key, releases signed with the same
   key need no new code.
4. The revision line of `THREAT_MODEL.md`.

---

## 2. Update and Commit Gradle Dependency Verification Metadata

Before cutting a release tag (and whenever dependencies or plugins change in
`build.gradle.kts` or `settings.gradle.kts`), regenerate Gradle's dependency
verification metadata on a machine with network access:

```bash
./gradlew --write-verification-metadata sha256 build
```

This creates or updates `gradle/verification-metadata.xml` with `<sha256>`
checksums for every resolved dependency and Gradle plugin. Running `build`
rather than `help` also records the artifacts that plugins resolve only while
they build, such as `protoc` and AAPT2.

1. Review the diff in `gradle/verification-metadata.xml` to ensure that every
   new or changed checksum corresponds to an expected dependency update.
2. Commit `gradle/verification-metadata.xml` at the release tag before building
   release artifacts.
3. With `gradle/verification-metadata.xml` present in the repository, subsequent
   `./gradlew` builds verify all resolved artifacts and fail on any SHA-256
   mismatch.

---

## 3. Build and Sign the Release APK

From the clean release tag:

1. Build the release APK with Gradle (`./gradlew clean assembleRelease`) on
   Linux x86-64, whose build tools the checksums cover, and sign it with the
   official Crumbles release signing key to produce `CrumblesApp.apk`.
2. Generate the APK file checksum alongside the binary (consumed by
   `setup_device.sh`, `setup_device.command`, and `setup_device.bat`):

```bash
sha256sum CrumblesApp.apk > CrumblesApp.apk.sha256
```

> **Note:** `CrumblesApp.apk.sha256` is the SHA-256 digest of the **APK file**
> and changes with every build. It is not the signing certificate fingerprint.

---

## 4. Verify the APK Signature and Extract the Certificate SHA-256

Verify the signed APK and print the signing certificate's SHA-256 fingerprint:

```bash
./tools/print_signing_cert_sha256.sh CrumblesApp.apk
```

The script runs `apksigner verify --print-certs CrumblesApp.apk` and formats the
`Signer #1 certificate SHA-256 digest` line as 32 colon-separated uppercase
hexadecimal octets:

```text
AA:BB:CC:DD:...:FF
```

You can also run `apksigner` directly:

```bash
apksigner verify --print-certs CrumblesApp.apk
```

Notice the three formats used across Crumbles for the same certificate digest:

* **Colon-separated uppercase hex (`AA:BB:CC:...`, 32 octets)**: printed by
  `./tools/print_signing_cert_sha256.sh` and displayed at the bottom of the
  Crumbles main screen (`App signing certificate (SHA-256):` from
  `R.string.app_signing_fingerprint`).
* **Unseparated lowercase hex (64 hex chars)**: printed directly by
  `apksigner verify --print-certs` on the
  `Signer #1 certificate SHA-256 digest:` line.
* **URL-safe Base64 (`PROVISIONING_DEVICE_ADMIN_SIGNATURE_CHECKSUM`)**: embedded
  in the Android Enterprise provisioning QR code JSON payload generated by:

```bash
./tools/generate_qr_payload.sh CrumblesApp.apk \
  "https://github.com/google/crumbles/releases/download/<tag>/CrumblesApp.apk"
```

As long as the official release signing key does not rotate, the signing
certificate SHA-256 fingerprint remains identical across releases.

---

## 5. Publish the GitHub Release

Attach `CrumblesApp.apk` and `CrumblesApp.apk.sha256` to the GitHub release and
include the following verification block in **every GitHub release note**:

```markdown
### Verification Metadata

* **Signing certificate SHA-256 fingerprint** (matches the in-app footer
  `App signing certificate (SHA-256):` and
  `./tools/print_signing_cert_sha256.sh CrumblesApp.apk`):
  `<AA:BB:CC:...:FF>`
* **Signing certificate SHA-256 (`apksigner verify --print-certs` hex)**:
  `<64-char-lowercase-hex>`
* **Provisioning QR `PROVISIONING_DEVICE_ADMIN_SIGNATURE_CHECKSUM`**
  (URL-safe Base64):
  `<url-safe-base64-checksum>`
* **APK file SHA-256 (`CrumblesApp.apk.sha256`)**:
  `<64-char-apk-file-sha256>`
```

Publishing the signing certificate SHA-256 in every release note ensures that
users following **[Verify your download](README.md#verify-your-download)** or
**[Verifying a provisioning QR code before you scan it][verify-qr]** have a
published reference value to check before installation, and at any later time
against the installed APK copied off the phone. The footer that Crumbles shows
is drawn by the installed app itself, so it is no check on its own.

`setup_device.sh`, `setup_device.command`, and `setup_device.bat` install the
downloaded APK only if `apksigner` finds that every signer of it is the
certificate given with `--expected-cert-sha256`, in
`CRUMBLES_EXPECTED_CERT_SHA256`, or typed in when the script asks for it. Also
give the fingerprint to partner organizations through a channel other than the
GitHub release, so that whoever could replace the release could not also
replace the fingerprint.

---

## 6. Verify That the Release Was Built From Its Tag

Gradle archive tasks keep no file timestamps and write their entries in a fixed
order, and the APK holds neither a dependency metadata block nor version control
information (see `build.gradle.kts`). So anyone can rebuild the release, from a
git checkout of the tag or from its source archive, and compare it with the
published APK:

1. Check that the published APK is signed with the release certificate:

   ```bash
   apksigner verify --print-certs CrumblesApp.apk
   ```

   The `Signer #1 certificate SHA-256 digest` must match the fingerprint
   published for the release.

2. From the release tag, build the unsigned release APK with the JDK and
   Android SDK Build-Tools versions that the release used:

   ```bash
   ./gradlew clean assembleRelease
   ```

3. Compare it with the published APK:

   ```bash
   diffoscope CrumblesApp.apk build/outputs/apk/release/crumbles-release-unsigned.apk
   ```

   Most systems package `diffoscope`: `sudo apt install diffoscope` on Debian
   and Ubuntu, `brew install diffoscope` on macOS, or `pipx install diffoscope`
   elsewhere. https://try.diffoscope.org/ also compares two files online.

   The only difference must be the signature, in the APK Signing Block of
   `CrumblesApp.apk`. Any other difference means that the published APK was not
   built from the tag.
